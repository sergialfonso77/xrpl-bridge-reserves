Independent proof of reserves for the XRPL ⇄ XRPL EVM bridge

A case study: how it was built, what it found, and where it stops. Figures are from 21 November 2026; the dashboard has the live ones.

Live dashboard · Source code (MIT)

The problem

Cross-chain bridges are where the largest sums have been lost in crypto, almost always through compromised custody (keys or signer quorum) or tokens minted without backing. XRP bridged from the XRP Ledger to the XRPL EVM through Axelar is held by a single multisig account on the XRPL, and the native gas token of the whole EVM chain is minted against it. Users trust that arrangement but have no continuous, independent way to check it.

This project is a read-only monitor: no keys, no signing, no custody. It answers one question anyone can re-run: is the XRP locked on the XRPL at least the XRP outstanding on every chain where it was minted?

Method: no number that was not measured

  • Only validated data. Failed or unvalidated transactions are ignored; amounts are read from delivered_amount, never Amount (the partial-payment trap); everything is integer drops, never floats.
  • Destinations are discovered, not listed. Chains holding the bridged-XRP token are enumerated from the Axelar ITS Hub. A chain with no tracked supply and no measurer turns the report unverified instead of being silently left out.
  • Every history read is checked against the ledger. Public XRPL nodes can drop transactions between pages without any error. History is accepted only in windows whose transactions add up to the account's real balance change; a window that does not is refetched from another node, and if it still fails the program stops rather than report partial data.
  • Conservative by construction. Where two sources disagree, the larger liability is used and an alert is raised; supplies are rounded up to drops.

What it found

  • An undocumented destination. Stellar holds about 24.5k bridged XRP. Neither the documentation nor the explorer lists it; only the ITS Hub does. A monitor built from the documented list would have undercounted liabilities.
  • Public XRPL nodes lose rows silently. In a scan of 5.8 million gateway transactions, 160 were missing from a naive pagination, including a 999 XRP payment. Balance-checked windows caught and repaired all of them. Anyone building on public XRPL history is exposed to this.
  • Where the surplus comes from. The ~7.5k XRP surplus is explained: gas fees paid on deposits stay in the gateway (4,503 XRP in total), plus direct funding and reserve top-ups, minus the transaction fees the gateway pays on releases. The account balance reconciles to the drop across 246 verified windows.
  • Deposits with no refund path. 203 deposits (about 38 XRP) carried an unusable gas memo (gas fee not below the amount, missing, or not an integer). They were never minted and the funds stay in the gateway.
  • A constant 2,999.24 XRP in the native supply of XRPL EVM that no bridge event accounts for, identical at two blocks 1,509 apart. It is not bridge-backed, so the dashboard overstates that chain's liability by that amount; the safe direction.
  • A recurring liveness probe. One XRPL account sends a 0.05 XRP transfer to the ITS contract on XRPL EVM every 12 hours (observed over the last days). It looks like an automated end-to-end check; its owner is not identified. It is useful as a delay measurement, and the reconciliation must treat it as ordinary traffic.

Event-level reconciliation

Beyond totals, each XRPL deposit is paired with the mint it should cause on XRPL EVM using only on-chain data: the mint event carries the original XRPL sender, the recipient and the exact amount. Pairs are made causally per (sender, recipient, amount), so no third-party index is needed. What remains is either an unmatched deposit (stuck, delayed or never delivered) or an orphan mint (no deposit behind it). Two lessons from validating it against live data: the sender's memo can encode the recipient address two different ways (raw bytes or its hex text), and the public EVM RPC load-balances over nodes that do not all hold old blocks, so a block or a log query can come back empty without error. The tool retries missing blocks and, when a deposit looks unmatched, re-reads the logs and takes the union before reporting it. Mints right after a window's end, or deposits just before its start, are classed as edge effects, not findings.

Operating it

  • A scheduled GitHub Actions job takes a snapshot, publishes this static page (strict Content-Security-Policy, no third-party code) and keeps its state on a separate branch. GitHub runs schedules best-effort, so in practice every few hours.
  • Telegram alerts for a new, changed or resolved problem, a change to the signer list, or a failed job. The job also fails visibly so GitHub notifies the owner.
  • The published JSON (latest, history) can be consumed by anyone, for example by a protocol that wants to gate the use of bridged XRP on the reserve status.
  • Third-party actions are pinned by commit SHA; the test suite (89 tests) runs on every push.

Limits, stated plainly

  • It detects and alerts; it cannot stop an attack. It is not an audit and not financial advice.
  • Freshness is hours, not seconds, so it is unsuitable for decisions that cannot tolerate delay.
  • Hedera and Stellar are measured through the ITS Hub's tracked supply. Stellar's token has no total-supply function and the public RPC keeps only seven days of events, so there is no independent on-chain check there yet.
  • The balance check cannot see a dropped transaction that did not move the gateway's XRP (for example a third-party token payment).
  • It trusts the public RPC providers and the ITS Hub for the facts it cannot verify directly.

What comes next

  • Reconcile the full bridge history (the two windows above are samples) and then run the reconciliation inside the scheduled job, alerting on deposits that stay unmatched past an agreed delay.
  • Measure XRPL EVM from its bridge events instead of its native supply, removing the 2,999.24 XRP offset.
  • An independent supply measurement for Stellar, and the same monitoring for any new destination as soon as the Hub lists it.
  • A versioned, documented schema for the published data so third parties can build on it.
